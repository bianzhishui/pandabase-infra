# ADR 0001：与业务仓库的边界

- 状态：已接受
- 日期：2026-11-08
- 决策者：项目负责人
- 关联：业务仓库 `docs/decisions/0002-tech-stack.md`、`0003-capability-only.md`、`docs/auth-contract.md`（反代不做鉴权）

## 背景

`mybmo-mcp` 本来的目标是「百度营销开放平台的 MCP 能力网关」——389 个接口收进 5 个工具。
但落地过程中为了「公网 + 多用户」引入了 Casdoor、PostgreSQL、Caddy、TLS、备份、升级脚本，
这些与「百度接口能不能调通」无关，却占了仓库一半的目录与大部分运维时间（一次 PG 大版本
迁移就是一小时）。

第二个业务即将接入。如果继续放在业务仓库里，每加一个业务就要把 Casdoor/PG/Caddy 复制一遍，
而且「谁能调哪个百度接口」这种业务语义会和「证书什么时候续期」混在同一个 backlog 里。

## 决策

1. **分仓**：`pandabase-infra` 承载共享底座，`mybmo-mcp` 退回纯业务。
2. **依赖方向单向**：infra 依赖「业务镜像 + 契约」；业务不引用 infra 的**任何文件路径**。
   业务只需要一份值清单（域、issuer、JWKS 地址、client_id、DSN 模板）。
3. **业务编排归业务仓库**。infra 不持有 `deploy/workloads/`，也不提供业务的 compose。
4. **契约只公布值，不规定变量名**。业务继续用自己的 `MYBMO_*`，infra 不要求它改名为 `MCP_*`。
5. **infra 不提供 Python 包**。鉴权代码（`TokenVerifier`）留在业务侧——把令牌校验放进 infra
   等于让 infra 侵入运行时，且与「反代不做鉴权」的安全边界冲突。
6. **ADR 编号各自从 0001 开始**：两个仓库生命周期不同，接续编号会让「ADR 0006 指哪篇」长期歧义。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 单仓库多目录（`apps/` + `platform/`） | 权限与发布节奏无法分离；一次 infra 变更会触发业务 CI |
| git submodule 把 infra 挂在业务下 | 部署机要处理两套 remote 与 submodule 状态；新人上手成本高 |
| infra 提供共享 Python 包（鉴权/审计） | 业务被 infra 的发布节奏绑住；且鉴权必须在业务进程内完成 |
| 反代统一鉴权（Envoy ext_authz / oauth2-proxy） | 与「反代不做鉴权」冲突（见 `docs/edge.md` 第三节）：反代注入的头可被直连回环伪造，等于留后门 |

## 后果

### 正面

- 业务仓库回到「能力网关」本身；`docs/` 里不再混有证书与数据库运维
- 第二个业务接入只需要：一个库、一个角色、一个 Casdoor 应用、一段 compose
- infra 可以在不影响业务代码的前提下换 IdP、换 PG 大版本、换反代

### 负面

- 一次业务发布可能同时改两个仓库（业务镜像 + infra 里的 client_id 白名单）
- 契约文档成为必须维护的资产；它一旦漂移，两边都会出问题
- 迁移期会短暂存在两份 compose（旧的在业务仓库），靠「不指向同一容器/卷」保证安全

## 重新评估条件

- 业务数 ≥ 5，或出现第二个需要**不同身份模型**的业务 → 重新考虑「平台是否该提供 SDK」
- 需要多机/HA → 本 ADR 的单机假设失效，PG 与网络模型都要重做
